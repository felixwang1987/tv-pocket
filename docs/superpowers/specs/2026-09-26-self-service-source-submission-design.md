# 影视口袋：自助添加来源设计

日期：2026-09-26。状态：待用户审核。设计来源：用户希望以后在网页中自行添加新发现的影视仓源或收集网站，并让它们参加每日检查。

## 目标与边界

用户从手机或电脑打开现有 GitHub Pages 网页，填写一个公开 HTTP(S) 链接，无须编辑 JSON 或提供 GitHub 令牌。由仓库所有者登录 GitHub 确认提交后，该链接成为每日检查的候选。点播与直播仍分别使用现有的两个固定导入地址；加入候选不等于播放通过，只有现有画面抽检成功的线路才进入实测合集。

支持两种输入：直接的单配置、多仓、线路合集、M3U/TXT 直播列表，或包含这些公开链接的收集网页。网页若要登录、运行脚本才能显示链接，或结构特殊而无法识别，仍需单独适配。账号、会员链接、私密网盘凭证和 token 不属于本功能。

## 方案选择

采用“网页表单 → 预填 GitHub Issue → 所有者确认 → GitHub Actions 纳入检查”。仓库 `felixwang1987/tv-pocket` 已确认开启 Issues。GitHub Pages 是静态托管，不能独立接收并持久保存配置；当前浏览器的 `localStorage` 也无法更新 GitHub Actions 使用的配置。直接在页面调用 GitHub 写入 API 则需要处理用户授权并增加暴露凭证的风险。Issue 表单使用用户已有的 GitHub 登录，不在 HTML 中存任何令牌。

GitHub 参考：[Issue 表单与预填参数](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)、[Issue 事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[工作流令牌触发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)。

## 用户流程

1. 现有首页增加“添加来源”入口，打开适合手机填写的表单：名称（可选）、公开链接、类型（直链／收集网页）、分类（普通／成人）。页面先检查 URL 格式和明显的凭证参数，并提示 Issue 在公开仓库可见。
2. “去 GitHub 确认提交”打开仓库 Issue 表单，字段已预填。用户确认并提交；网页不宣称此时已验证或已发布。取消 GitHub 提交不会改变仓库。
3. 只有 Issue 作者是仓库所有者、格式符合专用表单且字段通过服务端校验时，工作流才修改 `sources.config.json`。重复 URL 不添加第二份，结果在 Issue 中说明。
4. 接受新来源后，同一轮工作流运行现有单元测试、采集、实播检查、构建和 Pages 部署。来源目录显示可读或失败状态；只有符合当前验证标准的线路进入合集。完成或失败状态以简短中文回复写在该 Issue 中，并附 Actions 运行或网页地址。
5. 后续每天按原有 10:23 UTC 定时工作流复检；用户也可照旧手动运行。页面的“读取最新”仍只读取已发布结果，不启动采集。

## 组件与数据流

- `index.html`：新增表单入口、字段校验和生成预填 Issue 链接的逻辑；沿用现有访问码、视觉样式和无依赖静态页面结构。不给访客误导性的“已添加”提示。
- `.github/ISSUE_TEMPLATE/source.yml`：定义名称、URL、类型、分类字段及公开提交提醒。字段 ID 固定，供网页预填和服务端解析。
- `scripts/source_intake.py`：从 `GITHUB_EVENT_PATH` 读取 Issue JSON，校验作者、标题/表单字段、长度、URL、类型和分类；名称最多 100 字符、URL 最多 2048 字符；拒绝带用户信息、常见密钥参数或内网目标的地址；规范化 URL 并按 URL 去重；直接来源和收集网页分别最多容纳 100、30 项。以稳定格式原子写回 `sources.config.json`。Issue 文本只作为数据解析，不进入 shell 命令。
- `.github/workflows/update.yml`：在现有定时、手动、代码推送事件之外接收 `issues: opened`，仅让仓库所有者的专用 Issue 进入采集作业。Issue 事件先执行 intake，再运行现有检查和 Pages 部署；保持同一个并发组，避免两次运行同时提交快照。由于由 `GITHUB_TOKEN` 推送的配置提交不会再次触发普通 `push` 工作流，本次 Issue 运行必须自行完成采集与部署。
- `scripts/collector.py`：直链继续放在 `seeds`；收集网页放在 `source_pages`。保留现有 Discuz 正文解析，并增设有限制的通用 HTML 链接提取：只看静态可见文本和链接，忽略脚本/样式，挑出看起来是配置或直播列表的公开 URL。每页最多读取 500 KB、等待 10 秒、提取 30 条，总共最多处理 30 个收集网页；每日候选总上限仍为 360。继续使用现有公网地址与重定向校验。分类和原始网页出处向候选与目录传递。新提交的直链即使第一次检查失败，也在目录中显示失败原因，方便用户辨认。
- `README.md` / 网页说明：解释 GitHub 登录确认、公开可见性、状态查看、动态网页局限和合集入选标准。

## 失败与安全处理

访问码仅阻止随手打开网页，不能证明提交者身份；唯一授权依据是 GitHub Issue 作者为仓库所有者。非所有者的 Issue 不触发写入或网络检查。网页校验只为易用，工作流必须重新校验。拒绝本地/私网地址、非法协议、URL 内用户名密码、明显的 token/密码参数、过长字段和无效分类；实际抓取与每次重定向继续走受限公网网络层。采集绝不执行来源页面的 JS、JAR 或播放器插件。

地址无法访问、网页没有静态候选链接、内容格式不识别或实播失败时，保留明确的失败/未验证状态，不混入已实测合集。工作流出错时不发布半成品，旧网页和两个固定导入地址继续可用。配置写入应幂等；重复提交不增加重复候选。用户看到的 Issue 回复应区分“已纳入检查”和“已有可播线路”，不把两者混同。

## 验收

- 用测试 Issue 事件验证：仓库所有者的四类字段进入配置；非所有者、畸形 URL、私网/带凭证地址均不修改配置；重复提交无新增项；名称与分类原样受控保留。
- 用静态 HTML 样本验证通用收集网页只提取相关公开配置/直播链接，不采集导航、脚本、图片或账号参数；原有 Discuz/GBK 页面继续通过。
- 运行现有完整单元测试和本地构建，检查页面表单在桌面及手机宽度下可用，确保嵌入数据和两个固定导入 URL 不变。
- 上线后用仓库所有者的**无害测试链接**提交一次 Issue，确认工作流受理、去重、回复、采集和 Pages 部署；再核对网站数据与已发布文件。测试 Issue 不应让不可播内容进入实测合集。

## 非目标

不提供无登录匿名写入、不在网页保存 GitHub 个人令牌、不绕过网盘会员或第三方认证，也不承诺所有收集网站都能自动解析。版本一暂不做网页内编辑/删除已提交来源；可继续通过仓库配置或后续功能处理。
